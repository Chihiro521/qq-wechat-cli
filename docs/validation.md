# 本机验收记录

验证日期：2026-10-29。范围为 Windows x64、Node.js 24.14.1、Classic QQ 9.7.25.29417，以及本机迁移基线的微信数据库格式。下列测试使用最终发行核心；真实记录只存放在本机被忽略的 `.local` 中。

## 功能与异常处理

- Rust：11 项测试通过。包含 QQ 固定 DLL 参考向量、独立加解密往返、变化页与完整解密一致、错误密钥、微信独立 PyCryptodome 页对照、zstd、引用消息、系统标签与锁页位置作用域。
- 命令行与集成：21 项测试通过。覆盖两端明文 / 加密源的全功能链路、平台 / 账号隔离、旧配置导入、原文件不变、修改与删除、无符号时间和随机数、历史倒灌后的名称、分页、有限数量新消息的检查点、收藏时间字段变体、并发刷新、中途取消、恢复及导出。
- WAL 对照：同代新增提交、未提交尾部、代次重置、损坏头、已提交前缀截断和 checkpoint 后重新建库；增量结果与同一源快照的完整重建一致。
- Windows 看护：用测试子进程核对暂停、超时恢复、工作进程管道关闭恢复，以及进程身份不匹配时的处理。
- TS 类型检查通过。PE 导入表只包含 Windows 组件，未发现 QQ DLL、Python、独立 SQLite / zstd 或动态 VC 运行库依赖。

迁移前基线为 QQ 40 项测试、微信 8 项发行测试通过。旧 QQ 的未提交修复一并作为迁移源，原项目文件未被新项目覆盖。源码基线摘要见仓库中的 `docs/migration-baseline.json`。

## 真实快照对照

QQ 最终对照快照有 740,153 条消息，原始数据库与统一索引数量一致。抽查 1,266 条，由旧版 JavaScript 解析器对照标识、无符号时间 / 随机数、正文、类型、发送者及结构化元素，差异数为 0。

微信最终对照快照有 157,397 条消息，原始数据库与统一索引数量一致。抽查 1,916 条，核对标识、时间和原始类型，及文本 / 表情 / 系统 / 撤回的旧版呈现，差异数为 0。其他消息类型统一为带结构化元素的新模型，媒体占位文字随新模型调整。真实数据库会继续增长，因此不同轮次的总数可能不同。

在全新状态目录中重新进行首次同步，得到以下独立计时。微信这一轮通过显式旧配置导入复用页面验证过的密钥；仅登录但未装载全部目标库时，自动取钥可能返回 `KEY_NOT_FOUND`。

| 首次同步阶段 | QQ | 微信 |
| --- | ---: | ---: |
| 完整命令墙钟时间 | 160.032 s | 76.354 s |
| 快照复制 | 7.907 s | 1.372 s |
| 首次独立解密 | 12.199 s | 1.152 s |
| SQLite 完整性校验 | 2.211 s | 0.270 s |
| 首次索引 / 发布 | 137.025 s | 73.274 s |
| 核心峰值工作集 | 185.7 MiB | 128.6 MiB |

首轮索引是主要成本。不能把独立解密耗时等同于整次初始化耗时，也不能把不同数据轮次的测量直接解释为总体加速倍数。

## 测量方式

`research/benchmark.mjs` 对每项先预热一次、再运行 30 次，以完整 Node.js 命令进程的墙钟时间计算 P50 / P95，包含核心启动开销。搜索词为三字常见词，历史返回 50 条。基准依次执行，避免同时建索引干扰查询测量。

合成库包含 120,003 条消息，初次建索引约 31.6 秒。真实大库与合成库的最终查询指标、刷新指标及包安装结果记录在下方验收结果中。

微信这一轮基库与辅助库变化，触发了对应分片的完整解密，不能把它当作纯 WAL 追加耗时。纯 WAL 追加的正确性和只处理提交页面的行为由合成对照测试验证。

QQ 最末一轮未暂停客户端，使用双副本校验；此前可用暂停看护的一轮刷新为 59.085 秒，累计暂停 5 秒。复制和完整 SQLite 校验的耗时会受源库状态与磁盘缓存影响。

QQ 在源文件变化时仍需读取约 1.17 GB 源库、复制明文缓存，并扫描该分片判断消息变更；页面解密的减少不等于整次刷新只处理变化字节。普通缓存查询已显著缩短，变化源的刷新仍有上述成本。未变源的合成库刷新实测 149 ms（含启动），复制、解密、重建均为 0。

最终真实 QQ 的未变源刷新也确认复制字节数、解密页数和索引重建均为 0，核心检查耗时 2 ms（不含 Node.js / 核心启动）。

查询测量前，QQ 索引约 1.11 GiB，整个状态目录约 2.21 GiB；微信索引约 509 MiB，整个状态目录约 637 MiB；合成库状态目录约 364 MiB。状态包括明文缓存和搜索索引，发行包不包含这些数据。

## 旧版查询参考

对同一份 120,003 条消息合成源，额外运行旧 QQ 后端 5 次。旧版时间只含 Node.js 后端调用，新版时间包含完整 CLI 及 Rust 进程启动；两者采用各自对应的原始库 / 索引。

| 查询 | 旧版后端中位数 | 新版完整 CLI 中位数 |
| --- | ---: | ---: |
| 会话 | 67 ms | 106 ms |
| 历史 50 条 | 100 ms | 108 ms |
| 三字搜索 | 1,422 ms | 131 ms |

这一数据集的搜索路径有明显收益，小查询仍有进程启动成本。还存在工作量差别：旧版搜索会枚举、排序全部命中并返回 `totalMatches`；新版这一轮只返回 50 条与游标，不计算全部匹配数。因此上述表格不是等工作量的纯速度基准，也不能把两个搜索时间的比值当作整体提速倍数。

旧版复制 / 解密全流程未用同一快照重新测量；微信尚无同条件的新旧性能对照。现有结果支持“已建索引后的查询较快”，不支持“所有命令或两端完整流程都更快”的结论。

补充的当天导出运行在清空缓存后重新初始化，并与微信同时建库：QQ 全流程约 245.129 秒，其中首次索引约 212.510 秒、解密约 14.404 秒。首轮建库和磁盘负载是主要成本，前面的单轮数值不是耗时上限。

## 大批量导出

同一真实 QQ 会话分别导出 1,000、100,000 和该会话全部 152,562 条消息，逐条核对导出 ID 与索引排序一致。命令、读取与核对合计分别约 0.158、2.440、3.601 秒。

100,000 条约 61.3 MiB，152,562 条约 93.3 MiB。两轮核心峰值工作集约 9.0 MiB，Node.js 峰值分别为 113.7、114.0 MiB；消息总量增加后，内存保持在相近水平。流程使用 SQLite 游标、逐行协议和写入背压，ChatLab 成员也通过数据库游标输出。

## 安装包验收

真实 npm 压缩包已安装到独立临时目录，运行 PATH 仅保留 Node.js 与 Windows 系统组件，并清除开发核心路径覆盖。安装包中的加密 QQ / 微信合成数据均通过初始化、刷新、状态、查询、联系人、成员、收藏、未读、新消息、总结素材、导出及清理流程，npm 生成的 Windows 命令入口也通过版本检查。

安装包按白名单包含 13 个文件，压缩后约 2.5 MB；其中含编译后的 TS、x64 Rust 核心、说明和许可文件。真实状态、数据库、密钥、Python / Rust 开发环境及开发参考 DLL 均未包含。该验收是在独立安装目录与受限 PATH 中进行，并非新建 Windows 虚拟机。
